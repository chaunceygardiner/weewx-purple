weewx-purple change history
---------------------------

7.2 09/02/2026
--------------------
- The sample report is now a page rather than a headline.  It opens with a
  six-segment dial of the US EPA AQI categories, the category the current
  reading falls in, that category's health sentence, and all three
  particulate sizes -- pm1_0, pm2_5 and pm10_0 -- side by side; until now
  the page showed one of the three and spent the AQI color on a line of
  text.  Below it are the day's peak, average and low AQI (the peak with
  the time it happened), a count of the hours above Good, and a strip of
  the last 24 hours with one cell per hour colored by its category, so a
  smoke day is legible at a glance.  The four period plots stay where they
  were, in their own card behind the same Day/Week/Month/Year tabs.
- The page wears your station's name.  Its heading and browser title are
  now built from [Station] location in weewx.conf -- "Palo Alto, CA Air
  Quality" rather than "WeeWX-Purple Demo Page" -- because the report that
  ships with an extension is the one most stations actually put on their
  site, and it should not announce the extension to their visitors.  A
  station that has set no location gets a plain "Air Quality".  The
  location sits inside the translatable phrase rather than being glued to
  it, so each language places it and its preposition where it belongs.
- Twenty new translatable strings come with it -- the six category names,
  their six health sentences, the card headings and the tile labels -- and
  German, French, Dutch and Spanish translations of every one.  The
  sample report's own dictionary, lang/en.conf, also gains labels for pm1_0 and
  pm10_0, which the page now shows.
- The plots are a little taller (image_height 180 -> 230) and are drawn in
  the page's purple rather than the stock blue.  Particulate readouts now
  carry one decimal: a clean day reads 0.9, 3.0, 1.6 rather than 1, 3, 2.
- The options weewx-purple has its own default for -- poll_secs, and each
  source's port and timeout -- are now written into weewx.conf COMMENTED
  OUT rather than live.  Existing installations are untouched: an upgrade
  never rewrites an existing weewx.conf, so whatever your [Purple] section
  says today it goes on saying.  On a fresh install the option is visible
  with the value it is set to, but it is the extension that supplies that
  value, so a station that leaves it commented follows the default forward
  if a later release improves it; uncommenting it pins the station to the
  value written there.  What stays live is each source's enable and
  hostname -- the switch and the placeholder you have to replace with your
  own -- and the [StdReport] entries the report engine needs.  Each
  hostname's comment now leads with PLACEHOLDER, so the one kind of line
  that breaks the extension if you leave it alone says so first rather than
  last.

7.1 08/28/2026
--------------------
- ACTION REQUIRED for installations running WeeWX earlier than 4.6:
  weewx-purple now requires WeeWX 4.6 or later and will refuse to
  install or start on anything older.  The demo report's template uses
  $gettext and $lang, which arrived in WeeWX 4.6.0 (02/04/2022); on an
  earlier WeeWX the page did not fall back to English, it rendered the
  placeholders literally ($gettext("Day") in place of the tab labels,
  and a lang="$lang" attribute).  The version check compares the parts
  as integers, so the 4.10 series -- which sorts below "4.6" as text --
  is correctly accepted.
- A report set back to lang = en under a non-English [StdReport]
  [[Defaults]] lang now gets the US month/day year-plot axis back.  Each
  lang file overrides the year plot's x_label_format, but lang/en.conf
  set nothing, and a lang file is merged per report -- so an English
  report under [[Defaults]] lang = de rendered an English page with a
  German day-month axis.  en.conf now restates the default, and a test
  requires every lang file to set it.
- The skin no longer shadows its own translations.  skin.conf carried
  its own copy of the two observation labels and of the year plot's
  x_label_format, and WeeWX merges skin.conf back over the lang file, so
  those copies overrode the language -- but only for a report whose lang
  was set in skin.conf itself, where a German page kept English plot
  titles and a US month/day date axis.  Setting the language the
  documented way, in weewx.conf, was never affected.  Both values now
  live only in lang/<lang>.conf, and a test fails if either comes back.
  The lang files' [Units] [[Labels]] entries are gone too -- purple.py
  registers those two unit labels in WeeWX's process-global dictionary,
  which is consulted first, so a lang file could never have translated
  them and the entries were a trap for translators.  Set the language in
  weewx.conf ([StdReport] [[PurpleReport]] lang = de, or [[Defaults]]):
  weewx.conf is merged after skin.conf, and a stock WeeWX 5 weewx.conf
  carries [[Defaults]] lang = en, which overrides a lang set in skin.conf.
- An archive record whose interval is NULL no longer stops WeeWX.  The
  archive backfill added in 7.0 reads the record's own interval to work
  out the period it covers; a record that carries no value at all for it
  raised an error on WeeWX's main thread, which brings weewxd down with a
  traceback pointing at this extension.  Such a record now falls back to
  the configured archive interval, as one that omits the field entirely
  always has.
- The archive backfill now asks a proxy for the whole of the period it is
  filling, on an archive interval that is not a whole number of minutes.
  WeeWX reports the interval of such a record in fractional minutes -- 90
  seconds as 1.5 -- and the fraction was being dropped, so the backfill
  asked for the last 60 seconds of a 90 second period.  Affects software
  record generation only; with hardware record generation the interval
  comes from the console.

7.0 08/26/2026
--------------
- ACTION REQUIRED for existing installations that poll a purple-proxy:
  change timeout to 1 in every [[ProxyN]] section of weewx.conf.  A proxy
  answers out of its own database on the local network, so a second is
  ample; if it has not answered by then, it is down.  This matters more
  than it used to: the same timeout now governs the archive backfill
  below, which runs on WeeWX's main thread once per archive record, and a
  long catchup would otherwise wait out the timeout for every record.
  New installs are written with timeout = 1, and a [[ProxyN]] section that
  specifies no timeout at all now defaults to 1 rather than 10; an upgrade
  never alters an existing weewx.conf.
- The startup log now reports the archive interval this extension is
  working from, alongside poll_secs and fresh_secs.  It is the interval
  WeeWX itself archives on -- the console's under hardware record
  generation, weewx.conf's under software -- and it sets the window used
  for a record that arrives without one.
- Archive records for periods WeeWX was not running for -- the records a
  logger hands over at startup catchup -- now have pm1_0, pm2_5 and
  pm10_0 filled in from a purple-proxy's archive history, so an outage no
  longer leaves a gap in the pm columns.  The pm2_5 written is the same
  US EPA corrected value the live path stores.  Only periods this
  extension contributed no readings to are touched; a period WeeWX did
  see keeps the average it computed.  For a period that has just closed
  and that no proxy has archived yet, the proxy's current reading -- an
  average of the last two minutes -- stands in, but only while the period
  is still inside those two minutes.
  For any period further back that no proxy can answer for, the pm fields
  are left empty rather than filled with a value that says nothing about
  that period.  This requires a proxy: with only directly-polled sensors
  configured there is no history to ask for, and nothing changes.

6.0.1 08/24/2026
----------------
- A sensor whose BME280 has failed (or was never fitted) reports no
  temperature, humidity, dewpoint or pressure at all, and its readings
  are rejected.  The log now says so plainly, and names the chips the
  sensor did report finding (hardwarediscovered).  Previously this
  surfaced as a bare missing-key message, which sent users looking for
  a bug in this extension rather than at the sensor.
- The configuration stanza install.py writes into weewx.conf on a fresh
  install now carries explanatory comments -- what poll_secs does, that
  a Proxy is an instance of purple-proxy and a Sensor a piece of
  hardware, which values to replace.  Contributed by Tom Keffer.  An
  existing weewx.conf is untouched by an upgrade, as always.

6.0 07/31/2026
--------------
- The demo page is now translatable, entirely through WeeWX's own
  mechanisms.  Every string the page renders is either a gettext-style
  [Texts] key (the English string IS the key, and a report falls back
  to English one string at a time, so a partial translation is fine),
  an observation label ([Labels] [[Generic]]) or a unit label
  ([Units] [[Labels]]), all merged from lang/<lang>.conf over
  skin.conf.  The skin ships lang/en.conf, the reference dictionary:
  a test now fails if a rendered string is missing from it, or if it
  carries a string nothing renders.  Set the language per report with
  lang = <code> in weewx.conf ([StdReport] [[PurpleReport]]).
  Language support needs WeeWX 4.6 or later.
- German, French, Dutch and Spanish ship with the skin: lang/de.conf,
  fr.conf, nl.conf and es.conf are complete translations of the
  dictionary (a test keeps each complete, so new strings cannot ship
  untranslated; another pins the plot-period tabs to the translations
  of WeeWX's own Seasons skin).  Corrections are welcome -- file an
  issue -- as are further languages; a lang file is a self-contained,
  no-code contribution.
- The plots are now drawn with the skin's own OpenSans fonts (the same
  fonts WeeWX's Seasons skin ships): the built-in bitmap font cannot
  draw the accented characters of the translated plot labels.
- The pm2_5 label (the concentration plots' title) is now the standard
  short form PM2.5 -- PM2,5 in the translations, per European agency
  usage -- replacing "Concentration of Particles < 2.5 Micrometers".
- A user manual now ships in docs/, published at
  https://chaunceygardiner.github.io/weewx-purple/ (installation,
  configuration, fields in reports, translating, troubleshooting).
- Insane readings are now logged as warnings (were logged as info).

5.0.1 07/19/2026
----------------
Action required: none for typical installs.  Only if you added a
pm2_5_aqi/pm2_5_aqi_color column to your database schema, see below.

- $current.pm2_5_aqi and $current.pm2_5_aqi_color showed wrong,
  non-integer values in reports generated in real time by weewxd: WeeWX's
  accumulator folded the loop-injected AQI fields into the archive record
  with its default avg extractor (an averaged AQI is meaningless -- AQI is
  a non-linear transform of concentration; an averaged RGB color can
  belong to no EPA category at all), and $current used that record value
  instead of the AQI xtype.  (Found via a bug report against the sibling
  weewx-airlink extension, which shares this code; the bug has existed
  since AQI was first inserted into loop packets.)  The extension now
  registers extractor = noop for both fields (the same pattern WeeWX's
  own defaults use for windSpeed), so archive-record lookups fall through
  to the xtype and real-time, standalone, and graphed values all agree.
  An [Accumulator] entry in weewx.conf still takes precedence, so a
  deliberate override keeps working.
- If you added an AQI column to your database schema (not suggested by
  this extension's README, but possible), the accumulator no longer fills
  it.  Add to weewx.conf:
      [StdWXCalculate]
          [[Calculations]]
              pm2_5_aqi = prefer_hardware
              pm2_5_aqi_color = prefer_hardware
  This computes the stored values through the AQI xtype -- correctly
  EPA-rounded, unlike the averaged values stored before this release.

5.0 07/18/2026
--------------
Action required: none for typical installs.  If a report used
$span.pm2_5_aqi.sum, remove it (see below).

- The 'first' and 'last' aggregates of pm2_5_aqi/pm2_5_aqi_color produced
  invalid SQL and always failed.  Fixed.
- The 'count' aggregate of pm2_5_aqi returned the AQI *of the record count*
  rather than the count.  It now returns the count.
- The 'sum' aggregate of pm2_5_aqi is no longer accepted: the AQI of summed
  concentrations is not a meaningful quantity.  (Its SQL was invalid anyway,
  so it never actually worked.)
- Aggregates over a timespan whose length is a multiple of 24 hours (e.g.,
  a trailing 24-hour window) wrongly took the daily-summary fast path even
  when the span did not start at local midnight, silently including data
  from outside the span.  The fast path now requires both endpoints on
  local midnight.
- The Hazardous-category AQI slope was wrong: the code anchored AQI 500 at
  425.4 ug/m^3, but the EPA definition anchors it at 325.4 (May 2024 AirNow
  Technical Assistance Document, breakpoint-table footnote 4).  Hazardous
  AQIs were understated by up to ~100 points: 250 ug/m^3 is AQI 350 (was
  reported as 325); 325.4 ug/m^3 is AQI 500 (was reported as 400).
  As in prior releases, AQI values above 500 continue on the same slope
  (per the TAD); with the corrected anchor they begin at 325.4 ug/m^3
  rather than 425.4.  AQI values of 300 and below (PM2.5 up to 225.4
  ug/m^3) are computed exactly as before; readings only differ during
  Hazardous-category air.
  Because AQI is computed on demand from stored pm2_5, history in the
  Hazardous range (e.g., wildfire smoke events) will re-render with the
  corrected, higher values.
- A sensor temperature of exactly 0 degrees F caused pm2_5 to be dropped
  from loop packets.  Fixed.
- The EPA correction now applies the low-concentration formula at exactly
  343 ug/m^3, matching the EPA definition (previously high-concentration).
- Sensor sanity checks now accept whole-number readings (JSON integers)
  where floats are expected, reject JSON booleans where integers are
  expected, and reject a non-string DateTime with a clear reason.
- 'Found no fresh concentrations to insert' is now logged once per outage
  instead of on every loop packet; recovery is logged.
- Removed dead code: the unused purple-proxy helpers get_proxy_version and
  get_earliest_timestamp, and the unused utc_now.
- Tests moved to tests/ at the top level and expanded from 4 to 97 (96%
  coverage; uncovered: only the poller loop and import-time version
  guards); all aggregation SQL now executes against a real database in
  the tests.
- README rewritten.  Fixed a broken config example ([[Sensor]] instead of
  [[Sensor1]]) that made a copy-pasted config silently inoperable, and
  removed the bogus starup_timeout option (never read by the code).
